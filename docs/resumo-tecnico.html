3. Decisões de Arquitetura

Por que Vanilla JS no frontend web?

Projeto didático — alunos aprendem JS puro sem abstração de frameworks. Cada página HTML carrega só o que precisa, sem bundle ou build step.

Por que Expo e não React Native CLI?

Expo simplifica build (EAS), atualização OTA e acesso a APIs nativas sem configurar Xcode/Android Studio. SDK 54 garante estabilidade.

Por que Supabase e não Firebase?

PostgreSQL relacional é mais adequado para dados acadêmicos (notas, histórico, matrículas). Gratuito, sem vendor lock-in, SQL padrão.

Por que Express 5 e não 4?

Express 5 traz suporte nativo a async/await nos middlewares, removendo a necessidade de try-catch wrappers manuais.

Por que JWT e não sessions?

Stateless — não requer armazenamento no servidor. Escalável horizontalmente sem shared session store. Expiração de 24h.

6. Autenticação e Segurança

Fluxo de Login (JWT)

  • POST /api/usuarios/login → body: { email, senha }
  • → bcrypt.compare(senha, hash_armazenado)
  • → jwt.sign({ id, role, id_cargo, permissoes }, JWT_SECRET, { expiresIn: '1d' })
  • → Response: { token, usuario, permissoes }
  • → Frontend armazena token em localStorage (web) / in-memory (mobile)

Cadeia de Middleware

MiddlewareFunção
requireAuthExtrai e valida JWT do header Authorization: Bearer <token>
requireRole(...roles)Verifica campo role do usuário (legado)
requirePermissao(codigo)Verifica permissão granular via cargos_permissoes
requirePortalAtivo(codigo)Verifica se o portal está ativo na tabela portais
requireAdminMasterVerifica flag is_admin_master no cargo

Segurança

7. Fluxos Principais

Fluxo de Inscrição (Candidato → Aluno)

  • ➜ Candidato acessa portal-inscricao → escolhe curso
  • ➜ Preenche formulário + aceita LGPD
  • ➜ POST /api/inscricoes → status: EM_ANALISE
  • ➜ Admin aprova: PUT /api/inscricoes/:id → status_aprovacao: APROVADO
  • ➜ Aluno aceita matrícula → sistema cria matrícula + atualiza role para ROLE_STUDENT
  • ➜ Aluno acessa portal-escolar com dados completos

Fluxo de Lançamento de Notas (Professor)

  • ➜ Professor acessa portal-professor → clica "Lançar Notas"
  • ➜ Seleciona turma → disciplina → "Carregar Alunos"
  • ➜ Tabela de alunos aparece com inputs de nota
  • ➜ Professor digita notas → clica "Salvar"
  • ➜ POST /api/professor/notas → dados em historico_escolar

Fluxo de Autenticação na Catraca

  • ➜ Aluno abre app → aba "Acesso"
  • ➜ App gera código de 6 dígitos + QR code
  • ➜ POST /api/auth/gerar-codigo → salvo em codigos_acesso com expiração de 30s
  • ➜ Aluno apresenta QR/código na catraca
  • ➜ Catraca valida: POST /api/auth/validar-codigo
  • ➜ Server verifica: existe + não expirou + não usado → libera acesso

Fluxo de Requisição (Exemplo: Aluno vê histórico)

  • ➜ Aluno abre /portal-escolar/historico-escolar.html
  • ➜ Página chama initHistoricoPage() em scripts.js
  • ➜ GET /api/aluno/historico com header Authorization: Bearer <JWT>
  • ➜ Backend: requireAuth → requirePermissao('portal.escolar') → query Supabase
  • ➜ Supabase: SELECT * FROM historico_escolar WHERE id_matricula IN (matriculas do aluno)
  • ➜ Frontend renderiza tabela com notas por disciplina

9. Conceitos-Chave

JWT (JSON Web Token)

Token stateless com payload { id, role, cargo, permissoes }. Assinado com HMAC-SHA256. Não requer armazenamento no servidor. Expira em 24h.

bcrypt

Algoritmo de hash de senha com salt embutido. 10 rounds = ~10ms por hash. Resiste a ataques de rainbow table e brute-force. NUNCA armazenamos senhas em texto plano.

RBAC (Role-Based Access Control)

Permissões agrupadas em cargos. Cada cargo tem 58+ permissões granulares via tabela cargos_permissoes. Admin Master (is_admin_master=true) bypassa todas as verificações.

Expo Router (file-based routing)

Cada arquivo em app/ vira uma rota automaticamente. Similar a Next.js. Suporta layouts aninhados, tabs, modais.

Supabase

BaaS open-source. Fornece PostgreSQL gerenciado + API REST + Auth + Storage. Usamos apenas como cliente de banco (não usamos Supabase Auth). Autenticação é 100% custom via JWT.

CORS (Cross-Origin Resource Sharing)

Middleware cors() permite requisições de qualquer origem. Configuração didática — em produção, restringiria para origens específicas (Vercel, domínio próprio).

REST (Representational State Transfer)

API stateless baseada em recursos. Verbos HTTP: GET (ler), POST (criar), PUT (atualizar), DELETE (remover). Respostas sempre em JSON com códigos padronizados (200, 201, 400, 401, 403, 404, 500).
