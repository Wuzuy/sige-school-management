Início / Roteiro Técnico

Roteiro Técnico — SIGE

Guia universal para responder perguntas técnicas sobre o projeto. Cada aluno deve saber explicar os pontos abaixo com suas próprias palavras.

1. Visão Geral do Projeto

O que é o SIGE?

Sistema de Inscrição e Gestão Escolar — três portais em um: inscrição (candidato), escolar (aluno), secretaria (admin), além do portal professor e app mobile. Tudo online: inscrição, matrícula, notas, frequência, financeiro, carteirinha digital.

Qual problema resolve?

Elimina papelada, fila presencial e horário comercial. O aluno faz inscrição, acompanha notas, baixa documentos e resolve tudo digitalmente, sem precisar ir até a escola.

Quantos usuários suporta?

Backend stateless com Express + Supabase (PostgreSQL gerenciado). Escalável horizontalmente — sem limite fixo, depende do plano Supabase. O plano gratuito oferece 500 MB de banco e 5 GB de bandwidth.

Por que Vanilla JS no frontend web?

Projeto didático — os alunos aprendem JavaScript puro sem a abstração de frameworks como React. Decisão intencional de arquitetura para facilitar o aprendizado.

Por que Expo e não React Native CLI?

Expo simplifica o build (EAS Build), permite atualização OTA (Over-The-Air) e acesso a APIs nativas sem configurar Xcode ou Android Studio manualmente.

Por que Supabase e não Firebase?

PostgreSQL relacional é mais adequado para dados acadêmicos (notas, histórico, matrículas). Supabase é open-source, gratuito, sem vendor lock-in, e usa SQL padrão.

3. Backend — Arquitetura

Framework

Express 5.x. Fluxo de requisição: rota → middleware → controller → query Supabase → JSON response.

Cliente → HTTP → cors() → json() → auth middleware → handler → Supabase → JSON

Autenticação (JWT)

  1. Usuário envia { email, senha } para POST /api/usuarios/login
  2. Servidor compara senha com hash via bcrypt.compare()
  3. Gera JWT: jwt.sign({ id, role, id_cargo, permissoes }, JWT_SECRET, { expiresIn: '1d' })
  4. Retorna { token, usuario, permissoes }
  5. Cliente armazena token e envia no header Authorization: Bearer <token>

5. Frontend Web

Arquitetura

Múltiplas páginas HTML estáticas + JavaScript vanilla. Sem SPA — cada página é um HTML independente. Três portais + um portal professor SPA + portal secretaria SPA.

Como a autenticação funciona no frontend?

  1. POST /api/usuarios/login → recebe { token, usuario, permissoes }
  2. Token salvo em localStorage.setItem('auth', JSON.stringify(data))
  3. URL da API salva em localStorage.setItem('API_BASE_URL', url)
  4. Requisições usam Authorization: Bearer <token>
  5. Usuário pode configurar manualmente a URL da API via modal

│   └── explore.tsx    # Scanner catraca (*condicional)

Autenticação no mobile

In-memory — o token não é persistido (AsyncStorage não é usado). Fechou o app, deslogou. Gerenciado via services/api.ts + contexts/AuthContext.tsx com React Context API.

QR Code da Catraca

  1. App gera código de 6 dígitos + QR Code via react-native-qrcode-svg
  2. Código expira em 30 segundos (regeneração automática)
  3. Catraca lê QR/código e valida via POST /api/auth/validar-codigo
  4. Servidor verifica: código existe + não expirou + não usado → libera acesso

7. Perguntas Frequentes

Como o JWT é validado? ▶
O middleware requireAuth extrai o token do header Authorization: Bearer <token>, verifica com jwt.verify(token, JWT_SECRET). Se inválido ou expirado → retorna 401.
Onde fica o JWT_SECRET? ▶
Hardcoded como fallback 'secreta_sige_123' em middleware/auth.js. Pode ser sobrescrito via .env → JWT_SECRET.
Como as permissões são verificadas? ▶
A função getUserPermissoes(userId) faz um JOIN: cargos_permissoes → permissoes WHERE id_cargo = user.id_cargo. O resultado é cacheado em memória durante a requisição.
Qual a diferença entre ROLE e CARGO? ▶
role é campo legado (VARCHAR: ROLE_USER, ROLE_STUDENT, etc.). cargo é o sistema novo RBAC (FK → cargos.id). O novo sistema substitui o antigo, mas role ainda existe como fallback.
Como as senhas são armazenadas? ▶
bcryptjs com 10 rounds de salt. bcrypt.hashSync(senha, 10). NUNCA armazenamos senhas em texto plano. Na verificação: bcrypt.compare(senha, hashArmazenado).
O app mobile funciona offline? ▶
Não. Todas as telas dependem de API online. Não há cache offline implementado. O token de autenticação fica em memória — fechou o app, deslogou.
Como funciona o deploy? ▶
Frontend web na Vercel (auto-deploy do GitHub). Backend no Render (Node.js, porta 8080). Banco no Supabase (PostgreSQL gerenciado). Mobile via EAS Build (Expo).
O projeto tem testes automatizados? ▶
Não. O projeto é focado em funcionalidade e demonstração acadêmica. Não há testes unitários ou de integração.
Como uma inscrição vira matrícula? ▶
Candidato se inscreve → admin aprova (PUT /api/inscricoes/:id) → sistema atualiza role para ROLE_STUDENT e id_cargo para 5 (Aluno) → cria registro em matriculas → aluno acessa portal escolar.
Onde ficam os arquivos enviados (documentos)? ▶
A coluna arquivo_url na tabela documentos armazena URLs como texto. Os arquivos em si não são servidos pelo backend — é uma referência textual. Para produção, integraria com S3 ou Storage do Supabase.

9. Fluxos Principais (Passo a Passo)

Candidato → Aluno

  1. Candidato acessa portal-inscricao → escolhe curso
  2. Preenche formulário + aceita LGPD → POST /api/inscricoes
  3. Inscrição fica EM_ANALISE
  4. Admin aprova: PUT /api/inscricoes/:id → status_aprovacao: 'APROVADO'
  5. Sistema atualiza role para ROLE_STUDENT + cria matrícula
  6. Aluno acessa portal-escolar com dados completos

Professor lança notas

  1. Professor acessa portal-professor → clica "Lançar Notas"
  2. Seleciona turma → disciplina → "Carregar Alunos"
  3. Tabela de alunos aparece com inputs
  4. Professor digita notas → clica "Salvar"
  5. POST /api/professor/notas → salva em historico_escolar

Aluno acessa catraca via QR

  1. Aluno abre app → aba "Acesso"
  2. App gera código 6 dígitos + QR Code (expira em 30s)
  3. Aluno apresenta na catraca
  4. Catraca valida: POST /api/auth/validar-codigo { codigo }
  5. Servidor verifica existência + validade + não-uso → libera
